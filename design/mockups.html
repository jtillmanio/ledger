Comics dashboard

v4 changes: this screen used to be a mixed-media “Saturday” home — a books pace card sitting above a comics hero. It is now the comics dashboard at /comics, and the run list moved to /comics/runs. Books and Watch get the same shape.

  • The telescope replaces the hero cover. Three rails — the track’s 7 blocks, the block’s 5 runs, the run’s 381 issues — with brackets carrying the eye from coarse to fine. All three positions read at once, as geometry, which is the thing the spreadsheet column did well and a percentage cannot do. The ladder underneath names what the picture shows.
  • No new views needed. block_position already returns run 2 of 5 and block 1 of 7; block_progress and run_progress supply the issue counts and read counts. The rails are two ordered queries over views that exist.
  • Read is green, position is blue, held is amber. Same three meanings as the spine and the run list. The track hue rides the left edge of the track rail, so violet still means X-Men.
  • Cost and leverage are on the row. “costs 44 · opens 2” beats a tier badge, because the tier is a judgement you made once and the cost is a decision you are making now. Ewing — Defenders is shown deliberately: 13 issues, 4,642 to unlock.
  • The frontier replaces a progress bar. At 0.67% a catalogue bar is a lie told with a rectangle. Ready / soft-blocked / cold / owned-and-ready are the numbers that change what you open, and the catalogue total survives once, in grey, at the bottom.
  • Blocks are numbered, names optional. Block 1 shows its name; the “then block 2” row demonstrates the unnamed case, which is what nine block-less runs and most Avengers blocks look like today.
  • The thumb bar has one shape on every dashboard (D-25): the medium’s mark verb first and primary, then its second verb (+ batch here, ✓ finished on books, + Add on watch), then search. On desktop the same verbs sit in the page header, primary last; the run detail keeps the bottom bar at every width. Marking what you just read is one thumb tap on all three media types.
  • Sept 2026 — Up next. The comics answer to the books plan rail: your queue, one ordered list with no dates, showing the first five runs you haven't started. Start is on the top run, and every row has the queue’s ⋮⋮ reorder button (long press, or Space and the arrow keys) and a ⋯ row menu. It is the same row as the status tab’s queue (TASKS 1.10). A queued run can be blocked — Immortal Hulk is here with its amber 82 runs first, because wanting it next is legitimate and the badge says what that costs. Once you start a run it leaves this list and appears in Also in flight, but it keeps its place in the queue. Unlocked and waiting rows now carry + Up next, and a run already queued shows in Up next · #2 instead. ARCHITECTURE 2.16, TASKS 1.10.

Run list

v4 changes: runs group track → block, and every row carries what it costs instead of what tier you gave it. This settles open question 5 in HANDOFF §8.

  • Two levels of grouping, always. The dashboard's whole argument is that the block is the middle unit; a list that grouped only by track would disagree with the screen you arrived from. Blocks hold four to six runs, so 37 tracks do not become 37 walls of text. Block bands are the same filled bands the spine uses for eras — one device for "an ordered list, sectioned", at both levels.
  • Blocks are numbered, names optional. X-Men block 1 shows its name. Avengers block 2 has none and says so, with a Name it action rather than a blank.
  • Cost and leverage replace tier on the row. "costs 612" is a decision you are making now; tier is a judgement you made once. Tier survives as a sort option, not as a badge. Cost badges are amber, never red — an expensive run is held, not failed.
  • Blocked rows keep dimming and gain the run count that blocks them. Opacity alone is easy to miss; the badge says how far away it is.
  • Nine block-less runs group under No block at the foot of their track rather than vanishing.
  • Desktop: filters leave the scroll for a sticky rail, and the rail also carries the glossary — "costs" and "opens" are the two words on this screen that need defining once.

Run detail

v3 changes: the checkbox is a real 20px control with a tick; era headers are filled bands; a sticky action bar at the bottom.

  • Desktop: The run summary moves to a sticky rail so it stays with you down 381 issues, and the spine keeps one column — it is an ordered list and two columns would break the order.

  • Era headers are filled bands rather than hairline rows, so sections are unmistakable when you scroll 381 issues.
  • The bottom bar keeps Mark through here and Add issues reachable without scrolling to find them.
  • Optional issues get a grey badge instead of italics — a label beats a typographic hint.

Add issues — search

New, Sept 2026: every add starts from a search or from typing. This is the search half, and the default. Type it is the bulk-add screen. ARCHITECTURE 2.15, TASKS 1.3b.

  • Desktop: results on the left, what is staged on the right, so what you picked and where it lands can be checked side by side before anything is written.
  • Your catalog first. Balder #1 already exists because another run places it. It shows as yours, with in 1 run, and adding it creates only a placement, never a second issue.
  • Then Metron, on Enter, not on each keystroke. 20 requests a minute is plenty for one person adding issues and would not survive search-as-you-type. Responses are cached with the enrichment script's cache.
  • Cover and cover date resolve the volume. The ambiguity that bulk add makes you settle with year chips is settled here by looking at the cover. The volume year is in the label Metron hands back.
  • A Metron result arrives as a real issues row with metron_id, cover date and cover, label normalised to the bulk-entry grammar. Tapping it is the explicit accept, so the rule that no label reaches the database without one still holds.
  • The review step is shared with Type it. Staged rows go through the same review and the same one-transaction insert. Placements append, or go after an issue you choose.
  • Metron down or empty? Type it instead, with the query carried over. The API is a convenience, never a gate.

Book detail — a sheet, not a hover

Your question answered: a hover popup is the wrong shape here. A sheet over the list is the right one.

  • Desktop: On desktop the same intercepted route renders as a centred dialogue over the dimmed list rather than a bottom sheet. A right-hand panel was considered — it keeps the list usable — but it makes the detail permanently narrow, and the detail is the thing you came for.
  • Hover doesn't exist on Android, and that's where you'll use this most. A hover preview would give desktop a feature the phone can't have and leave the phone with nothing — backwards, given where the reading happens.
  • It also can't hold what justifies a detail view: notes, reading history, shelf membership, plan placement. A tooltip-sized popup forces you to cut exactly the content that made the feature worth building.
  • So: tap a row, detail slides up over the list. The list stays behind it with scroll position intact. Drag down, tap outside, or press back to dismiss.
  • It's a real route, not a modal component. Next.js intercepting routes render /books/[id] as this sheet when you arrive from the list, and as a full page on direct load or refresh. That buys three things a modal can't: the back button dismisses it, the URL is linkable, and refreshing doesn't dump you back to the list.
  • On desktop the same route renders as a centred modal. One component, two chromes.
  • The master list keeps inline status editing — the sheet is for reading about an item, the row is the fastest path to marking it read.
