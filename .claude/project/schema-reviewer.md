# schema-reviewer: Ledger

You are reviewing a change to the Ledger's Postgres schema or query layer. Data-layer files here are `drizzle/` (migrations, `meta/`, `down/`), `src/db/` (`schema.ts`, `queries.ts`, `export-tables.ts`), `etl/views.sql`, raw SQL anywhere, `etl/*.py` and the loaders (`etl/load.ps1`, `etl/load.sh`, `etl/rebuild.*`).

## Ledger checks, in priority order

1. Did derived data get stored in a column instead of computed in a view?
2. Did a per-user fact land in a catalog table (`runs`, `issues`, `books`) rather than a progress table?
3. Does every new read query filter `deleted_at IS NULL`, and does removing a placement soft-delete it rather than `DELETE` it?
4. Was `etl/views.sql` updated to match a schema change?
5. Is the migration reversible? A migration that drops, retypes or merges columns needs `drizzle/down/<tag>.sql` and an up → down → up test. Does it edit an already-applied migration?
6. Any query that will table-scan `issues` (~10,100 rows) or `run_issues` (~10,800) without an index?
7. Any raw SQL built by string concatenation rather than parameterized?
8. Does comics read state key on anything but the placement (`issue_progress.placement_id` → `run_issues.id`)? Does anything treat an issue as belonging to one run? `issues` has no `run_id`; placement, `type`, `notes` and `era_id` live on `run_issues`. A rollup above a single run must count `DISTINCT issue_id`, not sum run totals.
9. Does anything store or accept a typed run writer/artist instead of reading `run_credit_line`?
10. Can any enrichment or import path overwrite a value whose source is `hand` (`cover_date_source`, `story_title_source`, `issue_credits.source`), or rename a label without an accepted review?
11. Does any write to `issue_progress`, `book_status` or `read_events` store a date without its `*_precision`, or stamp `now()` on a read with no known date? The date is NULL exactly when precision is `none` (data model 2.17).
12. Does any test, fixture or script that truncates read `DATABASE_URL`? Only `TEST_DATABASE_URL` is allowed.

Report only gaps that affect correctness or the stated acceptance criteria. Do not report style preferences. Give file and line references.

## Migration tool (drizzle-kit)

- **Where.** `drizzle/NNNN_<name>.sql`, numbered from `0000`, generated by `npm run db:generate` from `src/db/schema.ts`; `drizzle/meta/_journal.json` and `drizzle/meta/NNNN_snapshot.json` come with each one. A generated file is hand-edited only to add `USING` to a retype. A `schema.ts` change with no new migration, or a migration with no `schema.ts` change, is a finding.
- **Rollback.** drizzle-kit is forward-only. A migration that drops, retypes or merges columns ships `drizzle/down/<tag>.sql` (`<tag>` = the migration's file name without `.sql`) and an up → down → up test asserting row values, including that a precision-`none` row is still `none` with a NULL date. `drizzle/down/0004_date_precision.sql` is lossy by design and is not the standard.
- **Applied = on `main`.** Migrations are not in `protectedPaths` (G-17). `npm run check:migrations` enforces journal = files, a down file for every drop or retype, `schema.ts` fully generated, and no migration already on `main` edited (standing rule 3). An edit to a migration this branch added is fine.
- **Views.** `etl/views.sql` is re-applied after every migrate (`npm run test:db:reset`, Release, the preview build). A column a view reads that is dropped or renamed must be handled in `views.sql` in the same diff.
